# Окошко

**«Окошко» - сервис онлайн-записи и автоматического заполнения освободившихся мест для бизнеса, работающего по расписанию.**

Первый реализованный MVP - частное демо барбершопа FORMA (Ташкент). TypeScript, React, Vinext, Cloudflare Workers и D1/SQLite. Код и миграции хранятся в Git.

## Продукт и границы MVP

Продукт рассчитан на развитие в парикмахерских, салонах красоты, автомойках, у репетиторов и в спортивных студиях. Общий процесс: запись или пожелание клиента → отмена → предложение подходящему человеку → подтверждение → обновлённое расписание.

В этой версии работает одна демонстрационная точка с фиксированным каталогом. Выбор отрасли, подключение нескольких компаний и изоляция их данных пока не реализованы. Планируется общее ядро с настройками: для салонов нужны кабинеты/оборудование, для автомоек - посты, для репетиторов - повторения, для студий - вместимость групп. Сначала проверяется пилот барбершопа; коммерческие условия других сфер требуют отдельной проверки. Подробности - в PRODUCT.md.

## Реализовано

- Три услуги длительностью 30/60/90 минут; два мастера, график и календарь в часовом поясе Asia/Tashkent.
- Онлайн- и ручная запись, проверка контактов, отмена, атомарный перенос и отметки о результате визита.
- Лист ожидания с датой, мастером, временным диапазоном и минимальным временем предупреждения.
- Последовательные предложения на 5/10/15 минут, подтверждение и отказ. Истёкшее предложение передаётся следующему подходящему человеку.
- «Хочу раньше»: исходная запись сохраняется до принятия нового предложения.
- Серверное хранение, уведомления внутри приложения, статистика заполненных окон и стоимости состоявшихся визитов.
- Демонстрационные записи добавляются кнопкой явно и только один раз. Это вымышленные имена и контакты без клиентской привязки; для них внешняя отправка не выполняется.

## Воспроизводимый локальный запуск

Проверенное окружение: Node.js 24, pnpm 11, Git. Не нужно копировать рабочую базу или секреты опубликованной версии.

```sh
pnpm install --frozen-lockfile
# Скопируйте .env.example в .dev.vars средствами своей ОС.
pnpm run db:migrate:local
pnpm run dev
```

В чистом клоне выбирается portable-профиль. Откройте `http://localhost:5173/`; для административного входа используйте `http://localhost:5173/admin` → «Войти в кабинет». Локальный mock-вход использует `seedy@sites.test` и доступен только на localhost/loopback. Он не включён в production-сборку. В `.dev.vars` для этого режима укажите `ADMIN_EMAIL=seedy@sites.test`. Существующая управляемая среда Sites имеет другой профиль и запускается своим supervisor; не переносите `.sites-runtime` из неё в чистый клон.

Команда миграций применяет все четыре SQL-миграции по порядку и ведёт журнал `d1_migrations`; повторный запуск безопасен. Она использует `wrangler.local.json`, локальную SQLite/D1 в `.wrangler/state` и никогда не передаёт `--remote`. `wrangler.local.json` используется только для миграций; сайт запускает Vite/Vinext.

Без настройки бота работают бронирование и внутренние уведомления. Для локального Telegram создайте отдельный тестовый бот, сгенерируйте `TELEGRAM_SECRET_KEY` (64 hex-символа) и задайте `APP_ORIGIN` в `.dev.vars`. Ссылки `localhost` из Telegram на другом устройстве не откроются: для реальной демонстрации используйте опубликованный сайт. Не используйте рабочий бот одновременно в двух окружениях: у `getUpdates` должен быть один обработчик.

```sh
pnpm run typecheck
pnpm test
pnpm run build
```

34 автоматические проверки: настоящий движок бронирования и обработчики API исполняются с изолированной SQLite и транзакционным адаптером D1. Telegram API в автоматических тестах имитируется. Отдельно выполнены 11 проверок на опубликованной версии: две даты, пересечение, перенос, очередь, предложение, принятие, повторное принятие, отказ и снятие заявки. Telegram подтвердил приём 13 тестовых сообщений; активных тестовых записей после проверки не осталось, существующие записи не изменились. Чтение сообщений пользователем этим журналом не подтверждается.

Для Sites используются штатные helpers установки/сборки/предпросмотра. При публикации Sites применяет миграции к рабочей D1; локальная и опубликованная базы разделены. Runtime-секреты `ADMIN_EMAIL`, `APP_ORIGIN` и `TELEGRAM_SECRET_KEY` настраиваются отдельно; ключ шифрования нельзя менять после подключения бота без повторной настройки. R2 не используется.

## Как устроено бронирование

`allocations` содержит записи, временные предложения и блокировки. `cells` хранит уникальный ключ «мастер|дата|30-минутный интервал». Все интервалы услуги резервируются одним транзакционным D1 batch: при конфликте откатывается весь batch, включая запись. Перенос отменяет старую и создаёт новую запись в одном batch; если новое время занято, старая запись сохраняется.

`waiters` хранит предпочтения и состояние заявки. Подбор использует точные правила, а не LLM. Предложение может занять освободившийся интервал, если вся длительность услуги помещается в него и в диапазон пожеланий. Очередь упорядочена временем добавления и ID. Цена задаётся серверным каталогом; клиентский payload цену не определяет.

`messages` — только внутренний журнал сообщений. Таймер проверяется на сервере, UI опрашивает состояние каждые 15 секунд. Когда приложение закрыто, обработка истёкших предложений ждёт следующего запроса: фоновый планировщик ещё не подключён.

## Клиентская часть и панель администратора

- `/` — самостоятельный клиентский интерфейс: мастер → услуга → дата/время → контакты. Разделы «Мои записи» и личные уведомления, отмена, перенос, лист ожидания и «Хочу раньше».
- `/admin` — отдельный интерфейс сотрудника. Доступ проверяется на сервере по Sites/ChatGPT-идентичности и настроенному `ADMIN_EMAIL`. При отсутствии входа показывается страница входа; другой аккаунт не получает кабинет.
- `/api/client` — клиентские операции. Связь с собственными записями хранится в случайной 256-битной HttpOnly-cookie (`Secure` на HTTPS, `SameSite=Lax`). API отдаёт только свои записи, заявки и сообщения. Для выбора времени выдаются обезличенные занятые интервалы без имён, контактов и токенов.
- `/api/state` — только администратор, включая GET. Сотрудник видит все записи и контакты, общую очередь, расписание и настройки. Клиентский API запрещает административные операции, даже если посетитель знает чужой ID и токен.
- Исторические записи предыдущей версии сохранены: у них нет привязки к клиентской cookie, и они доступны только администратору. Данные клиентов не присваиваются по совпадению телефона без проверки.

`ADMIN_EMAIL` хранится в runtime Sites как секрет и задаётся до публикации. Идентификационные заголовки доверяются только за Dispatch-периметром Sites; не развёртывать API за произвольным прокси, пропускающим поддельные identity headers. Для локальных API-тестов используется изолированная подстановка окружения, не включённая в продакшен.

Site сохраняет owner-private аудиторию; отделение клиентского интерфейса не делает его автоматически публичным. Доступ к «Моим записям» сейчас ограничен браузером, создавшим запись. Переход из Telegram через одноразовую защищённую ссылку восстанавливает кабинет в другом браузере. Вход по подтверждённому телефону/email ещё не подключён. Ручная запись администратора не привязывается к случайному клиентскому браузеру.

Telegram реализован как внешний канал и активируется после настройки бота и подключения клиента. Email/SMS/Web Push и AI-разбор пожеланий пока не подключены. Внутренний журнал сохраняется независимо от внешней доставки. Истёкшие предложения обрабатываются при следующем запросе; фоновый планировщик нужен для работы, когда все страницы закрыты. Для реального публичного запуска также нужны проверка контактов, rate limiting, канал доставки и согласованные правила обработки данных.

Один бизнес, фиксированные услуги, два мастера, общий рабочий график и ручные блокировки перерывов. Внешних календарей, платежей и многопользовательского SaaS пока нет. Прототип не подтверждает спрос или преимущество над конкурентами.

## Демонстрация за 5 минут

1. Войти в `/admin` и нажать «Добавить демонстрационные данные»: появятся три записи и Михаил в очереди на завтра.
2. Открыть запись Александра в 11:00 у Азиза и отменить.
3. Открыть уведомления: Михаилу предложено время; оно временно удерживается и не доступно обычной записи.
4. Принять предложение. Проверить расписание и счётчик заполненных окон.
5. Отметить визит состоявшимся. Стоимость появится в соответствующей метрике.
6. Перейти на `/`, пройти мастер → услуга → дата → контакты. Открыть «Мои записи»: видна только запись этого браузера, без демонстрационных клиентов.
7. Неавторизованный `/api/state` отвечает 403; `/admin` запрашивает вход владельца.

## Сторонние компоненты и AI при разработке

Использованы starter Sites/Vinext, React, Drizzle, Lucide и шрифт Golos Text (Google Fonts). Лицензии зависимостей сохраняются у пакетов; лицензия встроенных Sites-компонентов — в starter. Код создавался с помощью ChatGPT/Codex и проверялся TypeScript, автоматическими тестами и в браузере. Оплаченные внешние AI/SMS/email-сервисы не использовались.

Администратор может назначить время из листа ожидания: сразу подтвердить визит либо отправить предложение. Учитываются пожелания, свободные интервалы и время на дорогу; занятое окно не удаляет заявку. Обзор по умолчанию показывает все предстоящие записи с датами; фильтр выбранного дня и календарь доступны отдельно. Из уведомления можно открыть связанную запись.

Результаты комплексной проверки описаны в `QA.md`. Прочтение уведомлений администратором и клиентом независимо. При изменении исходного визита зависимое пожелание «Хочу раньше» закрывается, удержанное предложение освобождается. Пожелание администратора для клиентского визита сохраняет владельца. Автоподбор учитывает текущий график; календарь сохраняет видимость существующих визитов вне новых часов. Прошедшие периоды ожидания закрываются при очередном запросе.

## Telegram: настройка и границы версии

В runtime Sites настроены `APP_ORIGIN` и секретный `TELEGRAM_SECRET_KEY`; не менять ключ после сохранения бота без повторной настройки. Владелец создаёт отдельного бота в @BotFather (`/newbot`), затем вставляет токен в `/admin` → «Настройки» → «Telegram-уведомления». Сервер проверяет `getMe` и отсутствие чужого webhook. Токен сохраняется в D1 только в AES-GCM зашифрованном виде; его значение не возвращается в API или клиентский HTML.

Клиент в «Уведомлениях» создаёт одноразовую ссылку подключения, нажимает Start у бота и возвращается на сайт. Код живёт 10 минут, в базе хранится SHA-256. Один приватный Telegram-чат связан с одним клиентским кабинетом; совпадение телефона не используется для доступа. После привязки клиент получает сообщение о подключении и список имеющихся подтверждённых записей. Новые сообщения о записи, переносе, отмене и подходящем окне отправляются при обработке событий. Клиентская вкладка может быть закрыта. Отключение доступно на сайте и командой `/stop` (команда обрабатывается при синхронизации).

Так как Site остаётся owner-private, Telegram webhook извне недоступен. Для привязки используется `getUpdates` при открытом разделе уведомлений или ручной синхронизации администратора; это не фоновый обработчик. Кнопка сообщения открывает защищённую одноразовую ссылку на кабинет, а не исполняет действие записи GET-запросом. Пользователь подтверждает вход POST-запросом, получает свою HttpOnly-cookie и видит актуальное предложение; принять или отклонить его нужно на сайте. Ссылка действует 24 часа, истечение предложения всё равно проверяет сервер. Ссылки из сообщений нельзя пересылать: они предоставляют доступ к кабинету. Блокировка бота отключает данный чат после ошибки доставки.

Журнал `telegram_delivery` разделяет `sent`, `failed`, `uncertain`, `skipped`. Атомарная заявка на отправку защищает от параллельных повторов. При таймауте автоматического повтора нет: сообщение могло быть доставлено. Администратор может явно повторить отправку с предупреждением о возможном дубле (до трёх попыток). Ошибка Telegram не отменяет бронирование. Устаревшие предложения не отправляются. Автонапоминания до визита и работа очереди по таймеру при полностью закрытом приложении требуют отдельного фонового обработчика и в этой версии не активны.

Проверки: 34 автоматических сценария, включая тесты Telegram с имитацией API. Бот подключён пользователем; тестовое сообщение получено в настоящем чате, а при живом прогоне Telegram подтвердил приём 13 событийных сообщений.
